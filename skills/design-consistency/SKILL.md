# 일관성: 읽는 사람에게 무엇을 보장하나

## 먼저 물을 것 (비판적 질문)

1. **이 데이터가 잠깐 낡으면 실제로 무슨 일이 생기나?** 돈·재고·좌석 vs 좋아요 수. 데이터마다 따로 정한다.
2. **네트워크가 끊기면 거절할까(CP), 낡은 값이라도 답할까(AP)?** 끊기지 않은 평소엔 지연 vs 일관성(PACELC)을 고른다.
3. **사용자 본인이 방금 쓴 것만 보이면 되나?** 그렇다면 전체 강한 일관성 대신 read-your-writes 로 충분할 수 있다.
4. **순서가 뒤집혀 보이면 문제인가?** 댓글이 원글보다 먼저 보이는 식 → causal.
5. **강한 일관성이 필요한 범위가 정말 전체인가?** 대부분은 일부 데이터·일부 연산이다.
6. **보장 조건을 숫자로 말할 수 있나?** 예: W + R > N 이면 읽기가 최신 쓰기와 겹친다.
7. **읽기를 복사본(팔로워·읽기 전용 복제본·캐시)으로 돌리나?** 그러면 옛 값이 온다. '이 버전 이상' 또는 '이미 확정된 이 시점' 같은 조건을 걸고, 못 맞추면 기다리거나 원본으로 넘긴다.

## 선택지 한눈에

| 보장 | 뜻 | 비용 |
|---|---|---|
| Linearizable | 한 대처럼, 실제 시간 순서까지 | 합의 필요, 지연·가용성 손해 |
| Sequential | 모두가 같은 순서로 봄 (실시간 아님) | 전체 순서 필요 |
| Causal | 원인 → 결과 순서만 지킴 | 의존 관계 추적 |
| Eventual | 언젠가 같아짐 | 언제인지 보장 없음, 충돌 처리 필요 |
| 세션 보장 4가지 | 한 사용자 시점에서만 이상하지 않게 | 세션 고정 또는 버전 토큰 |
| 버전·시점 조건 복사본 읽기 | 요구한 버전·시점 이상인 사본만 답함 | 미달이면 대기·우회로 지연 |

## 흔한 함정

- CAP 의 C 와 ACID 의 C 는 다르다.
- "eventual" 은 언제 같아지는지 말해 주지 않는다. 얼마나 오래 낡을 수 있는지 측정하거나 정해야 한다.
- quorum 을 쓴다고 바로 linearizable 이 되지 않는다 (sloppy quorum, 동시 쓰기, 읽기 복구 타이밍).

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
