# 장애: 죽으면 어떻게 알고 견디나

## 먼저 물을 것 (비판적 질문)

1. **각 구성 요소가 죽으면 무엇이 멈추나?** SPOF 목록부터 만든다.
2. **죽은 것과 느린 것을 어떻게 구분하나?** 타임아웃 값의 근거는? 너무 짧으면 오탐, 너무 길면 늦은 복구.
3. **잘못 죽었다고 판단하면 무슨 일이 생기나?** 리더가 둘이 되나(스플릿 브레인)?
4. **옛 주인이 돌아와서 쓰기를 하면?** → 세대 번호(에포크) + 펜싱으로 저장소가 거절.
5. **네트워크가 반으로 끊기면 어느 쪽이 계속 일하나?** → 과반(quorum) 쪽만.
6. **재시도하면 중복 처리되나?** 멱등 키가 있나? 재시도가 몰려 장애를 키우지 않나(강의 밖: 지수 백오프, 서킷 브레이커)?

## 선택지 한눈에

| 감지 방식 | 판정 | 맞는 상황 | 약점 |
|---|---|---|---|
| 하트비트 + 고정 타임아웃 | 살았다/죽었다 | 소규모, 단순 | 네트워크 흔들림에 오탐 |
| φ accrual | 의심 정도(숫자) | 지연이 들쑥날쑥한 환경 | 임계값 조정 필요 |
| Gossip 기반 | 여러 노드 의견 종합 | 수백 노드 이상 | 감지가 퍼지는 데 시간 |
| 리스(lease) | 기한 지나면 자격 상실 | 리더·락 | 시계 어긋남 가정 |

## 흔한 함정

- 타임아웃을 짧게 잡아 오탐 → 페일오버 → 부하 증가 → 또 오탐 (연쇄).
- 장애 감지를 만들고 "옛 주인이 돌아오는 경우" 를 안 막기.
- 하트비트가 일반 데이터와 같은 줄에서 밀려 늦게 도착(HOL 블로킹).
- "응답이 없으니 실패" 로 보기. 처리됐는데 응답만 사라졌을 수 있다. 재시도할 거라면 받는 쪽을 멱등하게 만든다: 보내는 쪽이 요청마다 고유 ID를 붙이고, 받는 쪽은 확인·처리·기록을 한 덩어리로 하며, 기록은 재시도가 올 수 있는 기간만큼 둔다.
- 쓰는 저장소·라이브러리가 중복을 알아서 걸러 줄 거라 가정하기. 확인하지 않았다면 요청 ID나 조건부 쓰기(버전이 그대로일 때만 쓰기)로 직접 막는다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
