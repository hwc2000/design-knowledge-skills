# 배포·실행 환경: 어디서 돌리고 어떻게 바꾸나

## 먼저 물을 것 (비판적 질문)

1. **무엇 위에서 돌리나?** 물리 서버 / VM / 컨테이너 / 매니지드 서비스. 격리 수준, 한 대에 얼마나 많이 올리나, 누가 운영하나가 다르다.
2. **서버를 손으로 만드나, 코드로 만드나?** 다 지우고 다시 만들 수 있나(재현성)? 몇 분 걸리나? 그 시간이 복구 목표 안에 드나?
3. **코드와 실제 인프라가 어긋나지 않나?** 콘솔에서 손으로 고친 것(drift)을 어떻게 알아채나?
4. **인프라 상태 기록(state)은 어디에 두고, 둘이 동시에 바꾸면?** 잠금·공유 저장소·백업.
5. **바꾸기 전에 무엇이 바뀌는지 보나?** 계획(plan)을 읽고 '지우고 다시 만들기'가 섞여 있지 않은지 확인하나.
6. **새 버전은 어떻게 내보내나?** 롤링 / 블루-그린 / 카나리. 문제가 생기면 몇 명이 영향을 받나?
7. **되돌리는 데 얼마나 걸리나?** 롤백 절차가 있나. 데이터 구조 변경처럼 되돌리기 어려운 변경은 따로 다루나?
8. **설정·비밀값은 코드와 어떻게 분리하나?** → design-security
9. **반복되는 구성을 어떻게 묶나?** 모듈·변수로 입력과 출력만 드러내고, 하드코딩을 없앤다.

## 선택지 한눈에

| 배포 방식 | 하는 일 | 장점 | 대가 |
|---|---|---|---|
| 롤링 | 서버를 몇 대씩 차례로 교체 | 추가 자원 적음 | 잠시 두 버전 공존, 롤백 느림 |
| 블루-그린 | 새 환경을 통째로 띄우고 전환 | 즉시 전환·즉시 롤백 | 자원 두 배 |
| 카나리 | 일부 사용자에게만 먼저 | 피해 범위 작음, 실제 반응 확인 | 라우팅·관측 필요 |

| 실행 환경 | 격리 | 밀도·속도 | 대가 |
|---|---|---|---|
| 물리 서버 | 가장 강함 | 낮음 | 조달·교체가 느림 |
| VM | 강함 (OS 따로) | 중간 | OS 관리 부담 |
| 컨테이너 | 약함 (커널 공유) | 높음, 빨리 뜸 | 이미지·오케스트레이션 관리 |

## 흔한 함정

- 손으로 고친 설정이 코드에 없어, 다시 만들면 사라진다.
- 상태 파일 유실·동시 수정으로 실제 자원과 기록이 어긋난다.
- 롤백 계획 없이 배포하고, 배포 뒤 무엇을 보고 성공을 판단할지 정하지 않는다 → design-observability.
- 두 버전이 잠시 함께 도는 걸 잊고 호환되지 않는 변경을 낸다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
