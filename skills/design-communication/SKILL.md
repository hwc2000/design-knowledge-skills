# 통신: 어떻게 주고받나

## 먼저 물을 것 (비판적 질문)

1. **부르는 쪽이 결과를 지금 알아야 하나?** 아니면 나중에 알아도 되나 → 동기 / 비동기.
2. **받는 쪽이 꺼져 있으면 메시지를 보관해야 하나?** → 지속 / 일시. 1번과 곱하면 네 조합이 나온다.
3. **두 번 처리되면 무슨 일이 생기나?** → at-most / at-least / exactly-once. 실무 기본은 at-least-once + 받는 쪽 멱등 처리.
4. **받는 쪽이 느려지면?** 큐가 무한히 쌓이나? 백프레셔·타임아웃·버리기 중 무엇을 하나?
5. **순서가 중요한가? 어느 범위에서?** 전체 순서인가, 같은 키(주문 ID 등) 안에서만인가.
6. **소비자가 늘어나거나, 지난 메시지를 다시 처리해야 하나?** → Pub/Sub, 로그 기반(Kafka 류).
7. **큐를 새로 들일 만한 규모인가?** 브로커는 운영할 서버가 하나 더 생기는 것이다. 앱 하나·DB 하나면, 같은 DB 에 "보낼 일" 테이블을 두고 같은 트랜잭션으로 넣은 뒤 따로 꺼내 보내는 방식(아웃박스)이 먼저다 (강의 밖).

## 선택지 한눈에

| 방식 | 기다림 | 보관 | 맞는 상황 | 대가 |
|---|---|---|---|---|
| REST | 동기 | 없음 | 외부 API, 단순 조회 | 상대 장애가 그대로 전파 |
| gRPC | 동기·스트림 | 없음 | 내부 서비스, 다언어, 빠른 이진 직렬화 | 브라우저 직접 호출 제약, 스키마 관리 |
| 메시지 큐 | 비동기 | 있음 | 작업 분배, 완충 | 순서·중복 처리, 운영 부담 |
| 로그 스트리밍 | 비동기 | 오래 보관 | 여러 소비자, 재처리, 이벤트 기록 | 파티션·오프셋 관리 |
| Gossip | 비동기 | 없음 | 대규모 멤버십·상태 퍼뜨리기 | 퍼지는 데 시간(라운드) |

## 흔한 함정

- 비동기로 바꾸면 장애가 사라지는 게 아니라 늦게 드러난다. 실패한 메시지는 어디로 가나?
- exactly-once 는 메시지 시스템 안에서만 성립하는 경우가 많다. 끝단(DB, 외부 API)까지는 멱등 처리가 필요하다.
- 동기 호출이 줄줄이 이어지면 가장 느린 서비스가 전체 응답 시간을 정한다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
