# 시험공부 지식트리 아티팩트

사용자가 강의자료를 주며 지식트리를 아티팩트로 달라고 할 때의 고정 레시피.

**같은 폴더에 `profile.local.md`(개인 설정: 진로 목표, 과목별 문제 비중 등)가 있으면 시작할 때 먼저 읽는다.** 없으면 아래 기본값대로 한다.

**공용 부품은 같은 폴더의 `kit/`에 있다. 시작할 때 `kit/README.md`(짧다)만 읽는다.** CSS, 탭 전환, 트리 버튼, SVG 도우미, 드릴 엔진, 문제은행 엔진은 이미 완성되어 있으므로 다시 쓰지 않는다. 강의마다 새로 쓰는 것은 `body.html`(본문, `kit/body-skeleton.html`을 복사해 채움)과 `content.js`(그림 함수·트리 그림·도구·DRILLS·Q·TOPIC) 두 파일뿐이다. 완성 예시는 `kit/examples/ds16-*`(분산처리 16강)이고, 필요한 부분만 grep으로 찾아 읽는다. `reference-template.html`(13강)은 문체 예시로만 남겨 두며, 문체를 확인하고 싶을 때 트리 한 단원(약 100줄)만 읽는다. 통째로 읽지 않는다.

## 가장 중요한 것: 키워드 요약본 금지

과거에 실패한 형태(분산처리 14강 첫 버전): 트리 잎이 "SPOF·병목", "요청 N-1 + 응답 N-1" 같은 슬라이드식 키워드 조각이고, 설명은 다른 탭에 따로 있었다. 사용자는 이것을 "고수의 암기노트 요약본"이라며 거부했다.

올바른 형태(13강): **트리의 각 주제 노드를 펼치면 그 안에 선생님이 초보자에게 설명하듯 쓴 본문이 들어 있다.** 트리는 목차이자 본문이다.

각 주제(`details.topic`) 본문은 이 순서를 따른다.
1. **쉬운 설명** — 문장으로. 이 개념이 왜 필요한가(없으면 무슨 일이 생기나), 어디에 쓰이나, 어떻게 동작하나. 처음 나오는 용어는 그 자리에서 풀어 쓴다.
2. **비유** (`.box.analogy`) — 일상 경험으로.
3. **예시** (`.box.example`) — 구체적인 숫자·상황으로 한 번 따라가 보기.
4. **그림** — 메커니즘이 있는 주제면 인라인 SVG.
5. **시험에서는** (`.box.exam`) — 오답 보기로 나오는 함정, 헷갈리는 반대 진술.
코드·공식이 나오면 주석으로 한 줄씩 뜻을 단다. 함수는 한국어 기능 이름을 먼저, 코드 이름은 그다음.

요약표·외울 숫자·함정 문장은 **추가물**(비교·함정 탭)이지 본문을 대신하지 않는다.

## 페이지 구성 (13강과 같은 탭 레이아웃)

머리말(eyebrow: 과목·강·시험 대비, 제목, 한 문단 소개, 배지 범례 `출제`/`함정`/`계산`)

1. **지식 트리** 탭
   - **시작하기 전에: 왜 ___이 문제인가** — 이 강의가 푸는 문제를 구체적인 장면 하나와 그림 하나로 보여 주는 도입 카드. (13강: 서울·부산 서버 시계 차이로 입금·출금 순서가 뒤집히는 그림)
   - **강의 흐름** — 단원 순서 띠(쪽 번호 포함).
   - **먼저 알아 둘 용어** — 슬라이드가 설명 없이 쓰는 용어 용어집(`dl.gloss`). 12~16개 정도.
   - **지식 트리** — 모두 펼치기 / 모두 접기 / 출제 포인트만 펼치기. 단원(branch) → 주제(topic) → 위의 본문. 각 단원 첫 줄에 단원이 무엇을 하는지 한 문단(`li.lead`).
2. **비교·함정** 탭 — 단원을 한 표로, 개념 비교표, 외울 숫자 카드, "틀린 진술 vs 바른 진술" 표(10~16줄).
3. **공식·계산 연습** 탭 (계산이 있는 과목) — 공식 카드(왜 이런 공식인지는 트리에 있다고 연결), 손으로 풀고 정답 보기 하는 그림 문제, **무작위 계산 드릴**(값이 바뀌는 문제 생성기, 오답 보기는 흔한 실수로 만들기, 풀이 단계 표시). 계산이 거의 없는 과목이면 이 탭을 **그림 해석 연습**으로 바꾼다.
4. **문제은행** 탭 — 한 문제씩 카드, 유형·주제 필터, 틀린 문제만, 순서 섞기, 진행 점(dots), 숫자키 1–4와 ← →, 결과는 localStorage(try/catch). 데이터는 `[유형, 주제, 문제, 보기, 정답 index, 해설]` 배열.

## 사용자 요구 4가지 (매번 확인)

1. **초보자 눈높이** — 위 "가장 중요한 것" 그대로.
2. **그림** — 핵심 메커니즘마다 SVG 하나. 13강처럼 도입 그림, 시공간 다이어그램, 범위·구간 그림 등. 화살표에 라벨, 색은 CSS 변수만(라이트/다크 둘 다). 사용자는 그림 덕에 이해가 쉬웠다고 했으니 대부분의 주제에 그림이나 움직여 볼 수 있는 도구를 둔다. `artifact-diagramming` 규칙을 따른다.
3. **취업 연결은 가끔만** — 면접 질문·자소서 소재·코딩테스트와 진짜로 맞닿을 때만 본문 끝에 작은 박스(`.box.career`, 라벨 "취업에서는") 1~2문장. 페이지 전체에서 3~4번 정도. 사용자의 진로 목표는 `profile.local.md`에 있다. 그 파일이 없으면 이 박스는 넣지 않는다. 억지로 붙이지 않는다.
4. **문제** — 유형: 암기 / 상황(문제 상황 → 해결책 고르기) / 계산 / **그림 해석**(13강에는 없었음, 반드시 추가: 문제 데이터에 그림 키를 넣고 문제 카드 안에 SVG를 렌더). 전부 객관식 + 해설. 해설은 정답 이유와 오답이 왜 그럴듯해 보이는지까지. 분량은 자료에 따라 50~70개.
   - 비중은 과목별로 다르다. 사용자가 말해 준 과목별 비중은 `profile.local.md`에 있다.
   - 처음 보는 과목이면 비중을 한 번 묻는다. 물어볼 상황이 아니면 기본(암기 30 / 상황 25 / 그림 25 / 계산 20)으로 하고 답변에서 밝힌다.

## 절차

1. `kit/README.md`를 읽는다. 마크업 모양은 `kit/body-skeleton.html`, 그림·도구·드릴 코드 모양은 `kit/examples/ds16-content.js`에서 필요한 부분만 찾아 본다.
2. 강의자료를 읽는다. PDF 텍스트 레이어의 한글이 깨져 있는 경우가 많으니 페이지 이미지를 기준으로 옮긴다. 숫자·공식은 이미지와 대조. 슬라이드 그림과 규칙이 어긋나는 곳은 규칙대로 풀고 "참고"로 표시한다.
3. Artifact `action: "quickstart"`, `intent: "other"`, `design_systems: false`.
4. 스크래치패드에 `body.html`과 `content.js`를 쓴다. 각각 가능하면 Write 한 번으로 끝낸다. 제목은 "<과목 약칭> <N>강 <주제>" 형태(예: "로봇 7강 모션 플래닝").
5. 조립과 점검을 한 명령으로 돌린다:
   `python3 ~/.claude/skills/study-knowledge-tree/kit/build.py --title "…" --key <짧은영문키> --body body.html --content content.js --out page.html && python3 ~/.claude/skills/study-knowledge-tree/kit/test.py page.html`
   test.py는 문법, 문제은행 전 문항(그림·정답), 드릴 유형별 200회(보기 중복·정답), 트리 그림, JS 오류를 본다. `PROBLEM` 줄이 있으면 고치고 한 번만 다시 돌린다. 직접 만든 도구(슬라이더 등)는 test.py가 누르지 않으니 계산 함수를 node로 한 번 확인한다.
6. 게시 전 자체 점검:
   - 트리의 모든 주제가 문장 본문을 갖고 있나? 키워드 조각만 있는 곳이 있으면 다시 쓴다.
   - 각 주제에 "왜 필요한가"가 있나? 용어집이 있나? 도입 카드가 있나?
   - 그림 해석 문제가 있나? 계산 문제의 정답을 직접 다시 계산했나?
   - 취업 박스가 과하지 않나(3~4개)?
7. 게시하고, 답변 첫 줄에 "Written for: ..." 한 줄, 링크, 탭별 한 줄 설명, 슬라이드 밖에서 내가 추론한 부분을 밝힌다.

## usage 아끼기

- 도구를 한 번 부를 때마다 대화 전체(PDF 이미지 포함)가 다시 들어간다. 그래서 호출 수가 곧 비용이다. 목표는 quickstart → Write 2번 → build+test 1번 → 게시, 대략 5~7번.
- 공용 부품은 읽지도 다시 쓰지도 않는다. README와 예시는 필요한 부분만 본다.
- 화면 캡처는 새로 그린 SVG가 많아 겹침이 걱정될 때만, 잘라서 한두 장만 본다.
- 한 대화에서 여러 강의를 만들면 앞 강의의 PDF와 결과가 계속 쌓여 호출 한 번이 점점 비싸진다. 다음 강의는 새 대화에서 하자고 사용자에게 권한다.
- 키트 자체(CSS·엔진)를 고쳐야 하면 `kit/` 파일을 고친다. 이미 게시한 페이지는 다시 빌드해야 반영된다.

## 마지막 단계: 설계 스킬에 넣기 (반드시 허락받고)

게시한 뒤, 이 강의를 설계 지식 스킬(`design-*`)에 넣을지 **사용자에게 묻고, 허락할 때만** 진행한다. 묻지 않고 넣지 않는다. 사용자가 거절하면 지식트리만 주고 끝낸다.

- **파이프라인 위치:** 이 스킬 폴더의 실제 경로(바로가기를 따라간 곳) 기준 `../../pipeline/`. 과목 설정은 `pipeline/subjects/<과목>.json`, 쓰는 법은 레포의 `docs/design.md`.
- **묻는 방법 (한 번에):**
  - 과목 설정이 있으면: "이 강의를 설계 스킬에 넣을까요?" 와 함께 제안 표를 보여 준다: 단원 → 설계 질문 → 스킬 (복습·예고 같은 단원은 `배경`, 넣지 않음).
  - 설정이 없으면(처음 보는 과목): 설계 스킬에 넣을 과목인지부터 묻는다. 계산·이론 위주라 설계 판단에 쓸 일이 없는 과목이면 넣지 말자고 권한다.
  - 기존 설계 질문에 억지로 끼우지 않는다. 맞는 게 없는 단원이 많으면 새 설계 질문(새 스킬)을 제안하고, 이름·설명·먼저 물을 질문 초안을 보여 준 뒤 허락받는다.
- **허락하면:**
  1. `subjects/<과목>.json` 의 `lectures` 에 `{lec(선택), id, tags}` 를 넣는다 (새 과목이면 파일을 만든다). tags 는 단원 순서대로.
  2. 빌드한 page.html 을 스크래치패드의 HTML 폴더에 `<아티팩트 id>.html` 로 둔다. 다른 대화라 파일이 없으면 Artifact `read` 로 받아 온다.
  3. 스킬 폴더를 스크래치패드에 백업 → `extract.py <설정> <HTML폴더> <out.json> <id>` → `build_skills.py <out.json> <과목>` → 백업과 diff 해서 다른 강의 파일이 그대로인지 확인한다.
  4. 새 OV·SEE 규칙이 필요하면 같은 낱말을 쓰는 기존 주제를 먼저 검색하고 좁게 쓴다.
  5. 보고: 스킬별로 들어간 주제 수, 새 링크 수, 기존 파일 보존 여부. 커밋·푸시는 사용자가 따로 말할 때만.

## 수정 요청이 오면

"더 쉽게", "문제 더", "그림 추가" 같은 후속 요청은 같은 file_path로 수정해 같은 URL에 다시 게시한다. 다른 대화에서 온 요청이면 Artifact `read`로 받아 그 위에 고친다.
