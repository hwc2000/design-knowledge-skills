# 분할: 어떻게 나누고 어디서 찾나

## 먼저 물을 것 (비판적 질문)

1. **왜 나누나?** 용량이 넘치나, 쓰기 처리량이 모자라나? 읽기만 많다면 복제가 먼저다.
2. **어떤 키로 나누나?** 주요 쿼리가 그 키로 들어오나? 한 키에 몰리지 않나(핫스팟)?
3. **범위 조회가 필요한가?** 필요하면 범위 분할, 고르게 퍼뜨리는 게 우선이면 해시 분할.
4. **노드를 더하거나 빼면 얼마나 옮기나?** mod N 은 거의 전부 옮긴다 → 고정 파티션 수 또는 consistent hashing + 가상 노드.
5. **요청이 어느 노드로 가야 하는지 누가 아나?** 클라이언트 / 라우터·프록시 / 아무 노드가 받아서 전달.
6. **여러 파티션에 걸치는 쿼리·트랜잭션은?** 얼마나 자주 생기나?
7. **이름 → 주소:** 캐시 TTL 동안 옛 주소로 가는 건 괜찮나?

## 선택지 한눈에

| 방식 | 장점 | 약점 | 대표 |
|---|---|---|---|
| 해시 분할 | 고르게 퍼짐 | 범위 조회 불가 | Cassandra, DynamoDB |
| 범위 분할 | 범위 조회 빠름 | 핫스팟 (시간 순 키) | HBase, Bigtable |
| 고정 파티션 수 | 리밸런싱 단순 | 처음 개수 정하기 | Redis Cluster 16384 슬롯 |
| consistent hashing + vnode | 노드 변동 시 일부만 이동 | 구현·관찰 복잡 | Cassandra |

## 흔한 함정

- 파티션 키는 나중에 바꾸기 매우 비싸다. 처음 정할 때 접근 패턴을 확인한다.
- 시간이나 증가하는 ID 를 범위 분할 키로 쓰면 최신 파티션에 쓰기가 몰린다 → 솔팅(접두어).
- 작은 시스템에서 미리 샤딩하면 복잡도만 늘어난다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
