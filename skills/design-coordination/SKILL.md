# 조정: 누가 결정하나

## 먼저 물을 것 (비판적 질문)

1. **정말 조정이 필요한가?** 작업을 키로 나눠 각자 맡게 하면 경합 자체가 없어지지 않나?
2. **락이나 리더를 가진 쪽이 죽거나 멈추면(GC 멈춤, 네트워크 지연) 어떻게 되나?** → 리스(만료 시간) + 펜싱 토큰.
3. **직접 만들 건가, 검증된 걸 쓸 건가?** etcd·ZooKeeper·DB 락. 선출 알고리즘을 직접 짜는 건 거의 항상 손해다.
4. **과반이 없으면 결정을 멈추나?** 노드 수는 홀수인가?
5. **리더가 병목이 되지 않나?** 모든 쓰기가 리더를 거치면 리더 성능이 상한이다.

## 선택지 한눈에

| 방식 | 메시지·비용 | 장애에 | 맞는 상황 |
|---|---|---|---|
| 중앙 코디네이터 | 3개 메시지 | 코디네이터가 SPOF | 단순, 소규모 |
| Ricart-Agrawala (분산) | 2(N-1) | 누구 하나 죽어도 멈춤 | 거의 실무 X |
| 토큰 링 | 1 ~ 무한 | 토큰 분실 | 순서대로 돌아가며 |
| Raft 등 합의 기반 선출 | 과반 투표 | 과반 살아 있으면 계속 | 실무 기본 (etcd 등) |
| 단일 갱신 큐 | 큐 하나 | 큐 담당이 죽으면 | 한 프로세스 안 경합 |

## 흔한 함정

- 타임아웃만 있는 락은 안전하지 않다. 멈췄다 깨어난 옛 주인이 계속 쓴다 → 펜싱 토큰으로 저장소가 거절해야 한다.
- 락 하나에 모든 작업이 몰리면 분산한 의미가 없다.

design-failure (리더가 죽었는지 어떻게 아나), design-replication, design-performance (단일 갱신 큐)

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
