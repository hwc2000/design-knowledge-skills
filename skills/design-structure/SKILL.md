# 구조: 시스템을 어떤 모양으로 나누나

## 먼저 물을 것 (비판적 질문)

1. **무엇이 나누기를 강요하나?** 팀이 다르다, 배포 주기가 다르다, 부하가 크게 다르다, 장애를 격리해야 한다 — 이 중 없으면 하나로 두는 게 기본이다.
2. **결합이 어디에 남나?** 부르는 쪽이 받는 쪽의 주소·인터페이스·생존 여부·응답 시간을 알아야 하나? (강한 결합 4가지)
3. **조정 권한을 어디에 두나?** 중앙(단순하지만 SPOF) / 분산(복잡) / 하이브리드. 대부분 현실은 하이브리드다.
4. **이벤트 기반이 값을 하나?** 흐름 추적·디버깅·순서·중복 처리 비용을 감당할 이유가 있나?
5. **이벤트 소싱·CQRS 가 진짜 필요한가?** 이력 재생이나 읽기·쓰기 모델 분리가 요구사항에 있나, 멋있어서인가?

## 선택지 한눈에

| 스타일 | 결합 | 맞는 상황 | 대가 |
|---|---|---|---|
| 계층형 | 위→아래 강함 | 역할이 층으로 나뉘는 앱 | 층 건너뛰기 유혹, 전체 배포 |
| 객체·RPC | 호출 상대를 앎 | 내부 서비스 간 빠른 호출 | 상대가 죽으면 같이 멈춤 |
| REST(자원) | 인터페이스 통일 | 외부 공개 API | 세밀한 동작 표현 어려움 |
| 데이터 중심 | 공유 저장소로 간접 | 여러 작업자가 같은 데이터 | 저장소가 병목·SPOF |
| 이벤트 기반 | 서로 모름 | 소비자가 늘어나는 알림·후처리 | 흐름 추적·순서·중복 처리 |

## 흔한 함정

- 서비스를 나누는 순간 통신·일관성·장애 문제를 모두 떠안는다. 나누는 이유가 그 비용보다 커야 한다.
- "확장성 때문에" 는 근거가 아니다. 어느 부분이 얼마나 늘어나는지 숫자로 말해야 한다.
- 이벤트 기반으로 바꿔도 의존은 사라지지 않고 이벤트 형식으로 옮겨 간다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
