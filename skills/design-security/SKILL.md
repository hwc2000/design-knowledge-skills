# 보안: 누가 무엇에 닿을 수 있고, 무엇을 지키나

## 먼저 물을 것 (비판적 질문)

1. **이 데이터에서 무엇이 가장 중요하나?** 기밀성(새면 안 됨) / 무결성(바뀌면 안 됨) / 가용성(멈추면 안 됨).
2. **누구인지 어떻게 확인하고(인증), 무엇을 허락하나(인가)?** 사람 계정과 서비스 계정을 나누나. 공유 계정은 없나.
3. **권한은 최소인가, 항상 열려 있나?** 필요할 때만 잠깐 주고(JIT) 기록하나.
4. **밖에서 닿을 수 있는 입구는 몇 개인가?** 열린 포트·공개 API·관리 화면. 외부에 보여야 하는 것과 내부만 쓰는 것을 구역으로 나누나(DMZ·내부망).
5. **오가는 데이터가 암호화되나?** 인증서는 누가, 언제 갱신하나. 만료되면 서비스가 멈춘다.
6. **비밀번호·키가 코드·이미지·로그에 들어 있지 않나?** 비밀값 저장소, 커밋 전에 검사(일찍 찾을수록 싸다).
7. **사고가 나면 누가 무엇을 했는지 남아 있나?** 감사 로그를 지우거나 고칠 수 없게 두나.
8. **클라우드라면 어디까지가 내 책임인가?** 제공자와 나눠 지는 범위.

## 선택지 한눈에

| 통제 | 막는 것 | 대가 |
|---|---|---|
| 네트워크 경계 (방화벽·DMZ) | 밖에서 직접 닿기 | 안쪽은 따로 지켜야 함 |
| 최소 권한 · JIT | 계정 탈취 피해 확대 | 권한 요청 절차·운영 부담 |
| 전송 암호화 (TLS) | 엿듣기·바꿔치기 | 인증서 관리, 만료 장애 |
| 비밀값 저장소 | 코드·이미지 속 키 유출 | 저장소 자체가 중요 자산 |
| 감사 로그 | 누가 했는지 모름 | 저장 비용, 개인정보 관리 |

## 흔한 함정

- 경계 방화벽만 믿고 내부는 무방비로 둔다.
- 비밀값을 저장소에 한 번이라도 커밋하면, 지워도 기록에 남는다. 바로 교체한다.
- 운영 편의로 모두에게 관리자 권한을 준다.
- 인증서 만료처럼 보안 장치가 가용성 장애를 만든다 → design-observability 로 만료를 지켜본다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
