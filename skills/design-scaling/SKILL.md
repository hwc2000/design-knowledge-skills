# 확장: 사용자가 늘면 어떻게 늘리나

## 먼저 물을 것 (비판적 질문)

1. **무엇이 먼저 모자라나?** CPU·메모리·디스크·네트워크·DB 중 어디인지 숫자로 본다. 모르는 채로 서버부터 늘리지 않는다.
2. **한 대를 키울까, 여러 대로 늘릴까?** 한 대 키우기(scale-up)는 단순하지만 상한과 SPOF 가 있고, 여러 대(scale-out)는 상한이 높지만 나누는 장치와 상태 관리가 필요하다.
3. **서버가 상태를 들고 있나?** 세션·업로드 파일·로컬 캐시가 서버 안에 있으면 아무 서버로나 보낼 수 없다. 상태를 밖(공용 저장소)으로 빼서 stateless 로 만들 수 있나?
4. **요청은 누가 나눠 주나?** DNS / L4(주소·포트) / L7(URL·헤더·쿠키). 나눠 주는 장치 자체가 SPOF 는 아닌가?
5. **어떤 기준으로 나누나?** 라운드 로빈 / 가장 적은 연결 / 가중치 / 해시. 서버 사양이나 요청 무게가 고르지 않으면 단순 순번은 치우친다.
6. **죽은 서버는 어떻게 빼나?** 헬스체크 주기·실패 횟수·확인 경로(포트만인가, 실제 기능인가).
7. **언제 늘리고 줄이나?** 오토스케일 지표·임계치·대기 시간. 새 서버가 준비되는 데 걸리는 시간보다 부하가 빨리 오르지 않나?
8. **데이터 계층도 같이 늘어나나?** 앱 서버는 쉽게 늘어나도 DB 는 아니다 → design-replication(읽기 복제), design-partitioning(쓰기 분할).

## 선택지 한눈에

| 방식 | 하는 일 | 맞는 상황 | 대가 |
|---|---|---|---|
| Scale-up | 한 대의 사양을 키움 | 초기, 나누기 어려운 상태(DB) | 상한, 비용 급증, SPOF |
| Scale-out | 같은 서버를 여러 대 | stateless 앱, 큰 트래픽 | 분배 장치·상태 외부화 필요 |
| DNS 분산 | 이름 하나에 주소 여러 개 | 지역·사이트 단위 분산 | 캐시 때문에 장애 반영이 느림 |
| L4 분산 | 주소·포트로 전달 | 빠르고 단순한 분산 | 내용(URL·쿠키)을 못 봄 |
| L7 분산 | 요청 내용을 보고 전달 | 경로별 라우팅, 세션 유지 | 처리 비용, 설정 복잡 |
| 오토스케일 | 지표에 따라 대수 조정 | 부하가 출렁이는 서비스 | 준비 시간, 비용 예측 어려움 |

## 흔한 함정

- 세션 고정(sticky)에 기대다 특정 서버만 뜨거워지고, 그 서버가 죽으면 세션이 사라진다.
- 앱 서버만 늘리고 DB·외부 API 가 진짜 병목인 걸 놓친다.
- 분배 장치를 한 대만 둬서 새 SPOF 를 만든다.
- 규모에 비해 과한 구성(소수 사용자 시스템에 멀티리전·오토스케일). 확장 장치마다 비용과 운영 부담이 붙는다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
