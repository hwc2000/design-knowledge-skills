# 설계 비판 리뷰 (grilling 방식)

> 원본: mattpocock/skills 의 `grilling` (MIT, LICENSE 파일 참고). 한국어로 옮기고 이 작업 환경에 맞게 고쳤다.

## 진행 방식

사용자와 서로 같은 그림을 볼 때까지 끝까지 캐묻는다. 이것을 **결정 나무**로 그린다: 결정 하나에서 그것에 달린 다음 결정들이 가지처럼 뻗는다.

**라운드**로 진행한다. **지금 물을 수 있는 질문** = 앞선 결정이 이미 정해져서, 아직 못 들은 답을 짐작하지 않고도 물을 수 있는 질문. 이것들을 한 라운드에 한꺼번에 묻는다. 번호를 붙이고 질문마다 내 추천 답을 단다. 그리고 답을 기다린다.

라운드 형식:

```
❓ **Q1** - **<질문 제목>**: <질문 본문. 선택지가 있으면 함께>

➡️ <내 추천 답과 이유 한 줄>

---

❓ **Q2** - ...
```

질문은 **"네" 라고만 답하면 내 추천을 받아들이는 형태**로 쓴다.

답을 받으면 나무가 바뀐다. 정해진 결정이 다음 질문을 풀어 준다. 지금 물을 수 있는 질문을 다시 계산해서 다음 라운드를 묻는다. 이번 라운드의 다른 질문 답에 따라 달라지는 질문은 다음 라운드로 미룬다.

**사실 찾기는 내 일, 결정은 사용자 몫이다.** 파일·코드·문서에서 확인할 수 있는 건 사용자에게 묻지 말고 직접 찾는다 (원본은 서브에이전트를 쓰지만, 여기선 사용량 때문에 직접 찾는다. 사용자가 원할 때만 서브에이전트). 결정은 하나씩 사용자에게 묻고 기다린다.

**끝:** 모든 가지를 다 돌아서 몰래 가정한 게 남지 않으면 끝이다. 사용자가 "같은 그림이다" 라고 확인하기 전에는 구현하지 않는다. 끝나면 정한 것을 짧게 요약하고(결정 · 이유 · 포기한 것), 파일로 남길지는 사용자에게 묻는다.

## 분야 스킬 연결 (이 환경 추가분)

- 질문이 특정 설계 질문에 닿으면 그 스킬을 연다. 쓸 수 있는 design-* 스킬과 설명 한 줄은 스킬 목록에 있다 (과목이 늘면 스킬도 늘어나므로 여기에 고정 목록을 두지 않는다). 예: "DB 를 두 대로" → design-replication, design-failure.
- 그 스킬의 "먼저 물을 것" 을 질문 후보로 쓰고, 근거가 필요하면 references 에서 해당 주제만 찾아 "(과목 · 파일 이름)" 처럼 출처를 붙인다.
- 질문이 그 스킬 범위를 넘으면 `references/관련-주제.md` 링크를 따라가고, 거기 없어도 걸치면 다른 design-* references 를 직접 Grep 한다.
- 처음 라운드에서 모든 분야를 다 열지 않는다. 설계에 실제로 걸린 분야만 연다.
- 같은 개념이 여러 스킬·과목에 걸치면 아래 "겹칠 때" 규칙을 따른다.

## 질문할 때 같이 보는 관점

- **피해 범위:** 이게 틀리면 최악에 누가·무엇이 얼마나 다치나?
- **검증된 기술이 기본:** 새 기술은 꼭 필요한 곳 몇 군데만. 왜 그게 필요한지 묻는다.
- **되돌릴 수 있나:** 잘못 골랐을 때 바꾸는 비용. 되돌리기 어려운 결정(파티션 키, 데이터 모델)에 질문을 더 쓴다.
- **지친 사람 기준:** 새벽 3시에 장애가 나면 이 구조를 다룰 수 있나?
- **원래 어려운가, 우리가 어렵게 만들었나:** 복잡도가 문제 자체에서 오는지 선택에서 오는지.
- **규모를 숫자로:** "많다", "빠르다" 대신 사용자 수, 초당 요청, 허용 지연을 묻는다.
- **과잉 설계 아닌가:** 지금 규모·요건에 비해 비싼 장치(멀티리전, 샤딩, 서비스 분리)를 넣고 있지 않나. 각 장치가 막는 위험과 드는 비용을 말할 수 있나.
- **알아챌 수 있나:** 이게 고장 나면 어떤 신호로, 누가, 몇 분 안에 아나.
- **누가 들어올 수 있나:** 새 입구(포트·API·권한·키)가 생기면 공격 표면이 늘어난다.

## 지키는 것

- 강의 내용은 근거이지 정답이 아니다. 실무 관행·최신 동향과 다르면 그렇다고 말한다.
- 특정 제품·버전을 고르는 질문에서만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 한다.
- 맞장구치지 않는다. 사용자의 답이 약하면 왜 약한지 말하고 다시 묻는다. 반대로 충분하면 더 끌지 않는다.

## 겹칠 때 (여러 스킬·과목에 같은 개념)

1. **배치:** 주제 본문은 설계 질문 하나(주 태그)에만 있고, 걸치는 다른 스킬에는 `references/관련-주제.md` 에 링크만 있다. 같은 개념이 다른 과목에도 있으면 같은 스킬의 `references/<과목>/` 에 따로 있다.
2. **질문이 두 스킬에 걸치면** (예: "DB 를 두 대로" → 복제 + 장애): 둘 다 열되, 각 스킬에서 지금 질문에 필요한 주제만 Grep 으로 읽는다.
3. **과목별 관점이 다르면** 고르는 기준: "왜 / 무엇을 보장하나" 는 원리 과목(예: 분산처리), "어떻게 구성하고 운영하나" 는 구성 과목(예: 인프라). 둘 다 걸리면 둘 다. 같은 것을 다른 이름으로 부르기도 한다(예: 이중화 ↔ 복제·페일오버, 수평 분할 ↔ 샤딩·Partitioning) — 낱말이 달라도 같은 질문이면 함께 본다.
4. **내용이 서로 다르면** 합치거나 하나를 몰래 고르지 않는다. 둘 다 출처와 함께 보여 주고 어떤 조건에서 무엇이 맞는지 말한다.
