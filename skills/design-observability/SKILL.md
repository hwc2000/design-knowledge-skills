# 관측: 무슨 일이 일어나는지 어떻게 아나

## 먼저 물을 것 (비판적 질문)

1. **사용자가 아프다는 걸 어떤 숫자로 아나?** 지연·에러율·처리량·포화(자원이 얼마나 찼나). CPU 만 보고 사용자 경험을 놓치지 않나?
2. **임계치의 근거는?** 평소 값을 재 봤나. 근거 없는 숫자는 오탐이나 놓침이 된다.
3. **알림은 누가 받고, 받으면 무엇을 하나?** 할 일이 없는 알림은 소음이다. 알림 피로가 쌓이면 진짜 알림도 무시된다.
4. **얼마나 오래 넘어야 울리나?** 순간 튐과 지속을 가른다(대기 시간 뒤 발송).
5. **원인을 찾을 때 무엇을 보나?** 로그를 한곳에 모으나, 요청 하나를 여러 서비스에 걸쳐 따라갈 수 있나(요청 ID·트레이스)?
6. **얼마나 오래 보관하나?** 비용·규정·사고 조사에 필요한 기간.
7. **관측 시스템이 죽거나 늦으면?** 그 사실은 누가 아나?
8. **일부러 고장 내 봤나?** 장애를 주입해 신호가 실제로 뜨는지, 장애 종류마다 신호가 어떻게 다른지 확인한다.

## 선택지 한눈에

| 신호 | 답하는 질문 | 강점 | 대가 |
|---|---|---|---|
| 메트릭 | 얼마나·언제부터 | 싸고 빠름, 추세·알림 | 왜 그런지는 모름 |
| 로그 | 무슨 일이 있었나 | 자세한 원인 | 양이 많고 비쌈, 검색 필요 |
| 트레이스 | 요청이 어디서 느렸나 | 서비스 간 경로 | 계측 작업, 표본 추출 |

## 흔한 함정

- 모든 걸 모니터링하고 모든 걸 알림으로 보낸다.
- 서버마다 로그가 흩어져 있어 장애 때 하나씩 접속해 본다.
- 로그에 비밀번호·개인정보를 남긴다 → design-security.
- 배포·설정 변경 시점이 그래프에 없어, 원인과 변경을 잇지 못한다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
