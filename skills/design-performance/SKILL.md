# 통신 성능: 어떻게 빠르게 하나

## 먼저 물을 것 (비판적 질문)

1. **측정했나?** 어디가 병목인지 숫자가 있나. 지연(한 요청이 얼마나 걸리나) 문제인가, 처리량(초당 몇 건) 문제인가?
2. **왕복을 기다리느라 노는가?** → 파이프라인 (응답을 기다리지 않고 다음 요청을 보냄).
3. **요청 하나하나의 고정 비용이 큰가?** → 배칭. 대신 지연이 늘어난다. 배치 크기와 "언제 내보낼지"(크기·시간) 조건은?
4. **순서가 깨지면 안 되나?** 파이프라인 + 재시도는 순서를 깨뜨릴 수 있다 → 연결 하나·순번.
5. **연결이 수천~수만 개인가?** → 이벤트 루프·epoll. 단, CPU 무거운 작업은 루프를 막는다.
6. **공유 상태를 두고 락 경합이 심한가?** → 단일 갱신 큐(한 작업자만 상태를 고침).

## 선택지 한눈에

| 기법 | 줄이는 것 | 대가 |
|---|---|---|
| 파이프라인 | 왕복 대기 | 흐름 제어 필요, 순서·재시도 복잡 |
| 배칭 | 요청당 고정비 | 지연 증가, 배치 단위 실패 처리 |
| 단일 채널 | 연결 비용, 순서 문제 | 한 연결이 병목 |
| 단일 갱신 큐 | 락 경합 | 큐 하나가 처리량 상한 |
| 이벤트 루프·epoll | 연결당 스레드 비용 | 블로킹 코드 금지 |

## 흔한 함정

- 측정 없이 최적화부터 하기.
- 배칭으로 처리량을 올리고 지연 요구(p99)를 잊기.
- 캐시는 아직 references 에 자료가 없다. 답할 땐 (강의 밖) 으로 표시하고, 다른 과목 자료가 생기면 그쪽을 먼저 본다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
