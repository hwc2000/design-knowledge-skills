# 충돌·순서: 동시에 쓰면, 무엇이 먼저인가

## 먼저 물을 것 (비판적 질문)

1. **같은 데이터를 두 곳에서 동시에 고칠 수 있나?** 막을 건가(단일 리더·락), 허용하고 나중에 풀 건가?
2. **충돌하면 한쪽을 잃어도 되나?** 안 된다면 LWW(마지막 쓰기 승리)는 쓰지 않는다.
3. **합치는 규칙을 정할 수 있는 데이터인가?** 집합·카운터·편집 문서 → CRDT 가 맞을 수 있다.
4. **벽시계로 순서를 정하나?** 서버 시계는 어긋난다. 어긋남을 얼마나 허용하나?
5. **필요한 게 인과 관계만인가(vector clock), 전체 순서인가(Lamport + 동률 처리, 또는 합의)?**
6. **읽을 때 어느 시점 값을 보나?** 스냅샷 읽기(MVCC)가 필요한가?

## 선택지 한눈에

| 방법 | 하는 일 | 대가 |
|---|---|---|
| LWW | 늦은 쪽이 이김 | 조용한 데이터 손실, 시계 오차에 취약 |
| 형제 보관 + 앱 병합 | 충돌 값을 다 두고 앱이 합침 | 앱 코드 복잡 |
| CRDT | 규칙대로 자동 수렴 | 쓸 수 있는 자료형 제한, 메타데이터 증가 |
| Version vector | 동시 여부 판정 | 노드 수만큼 크기 증가 |
| HLC | 실제 시간 근처 + 인과 순서 | 시계 오차 한도 가정 |
| TrueTime + 커밋 대기 | 외부 일관성 | 특수 시계 장비, 대기 시간 |

## 흔한 함정

- LWW + 시계 어긋남 = 아무도 모르게 쓰기가 사라진다.
- 타임스탬프가 같을 때 처리 규칙을 안 정하기.
- "동시에 안 일어날 것" 이라고 가정하기. 재시도·오프라인이 있으면 일어난다.

## 쓰는 규칙

- references 는 내 강의 정리다. 근거로 인용하되 정답으로 쓰지 않는다. 실무 상황과 맞지 않으면 그렇다고 말한다.
- 특정 제품·버전(Kafka, etcd, Redis 등)을 고르는 순간에만 최신 상황을 검색하고 날짜를 붙인다. 확인 못 하면 모른다고 말한다.
- references 는 통째로 읽지 말고 아래 목록에서 파일을 골라 Grep 으로 주제(`### 제목`)만 찾아 읽는다.
- 질문이 이 스킬 범위를 넘으면 `references/관련-주제.md` 를 본다. 거기 없어도 걸치는 것 같으면 다른 design-* 스킬의 references 도 직접 Grep 한다. 링크는 지름길일 뿐 전부가 아니다.
- 같은 개념이 여러 과목 폴더에 있으면 둘 다 본다. 내용이 다르면 출처와 함께 둘 다 보여 주고 어떤 조건에서 무엇이 맞는지 말한다. 몰래 하나를 고르지 않는다.
- 강의에 없는 일반 지식을 덧붙일 땐 "(강의 밖)" 이라고 표시한다.
